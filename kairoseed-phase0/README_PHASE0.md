# KAIROSEED Phase 0 — Synthetic Governed Tool Execution

**Scope:** testbed only, never real users, data, permissions, payments, production services, or system effects. Canonical research specifications stay frozen and separate from this branch.

**Purpose:** implement a falsifiable, small, split-process mock authorization gate. Successful unit tests mean the mock fixture behaved as expected under tested conditions; they **do not** prove actual complete mediation, independent security enforcement, WORM preservation, kernel containment, cryptographic attestation of time, or JIREH C3/C6.

## Files and process responsibility

- `scope.json`: exact synthetic scope and permitted `share` operations on `doc_A` and `doc_B`. Nothing else is inferred from memory or an agent's persistence.
- `gat.py`: separate authorization process; HMAC-checks a test token, scope, current local service time and separate ledger revocation query; signs scoped decision receipts; **no execution**.
- `pep.py`: synthetic IPC PEP and fixture processes; checks GAT decision receipt before updating the test booleans. `jireh_trap()` is a **simulated denial hook**, not actual OS, seccomp, eBPF, or process confinement.
- `stranger.py`: distinct process with a read-only fixture-observer channel; computes before/after differences and identifies mismatches. No import of GAT or PEP.
- `ledger.py`: separate append-only API for JSONL records with an SHA-256 hash chain; GAT receives a query-only ledger channel. **Not a physical WORM store**. Privileged rewriting of all records may evade this mechanism without independently retained anchors.
- `audit.py`: separate read-only audit process that checks the ledger's chain and simplified effect-set inclusion `Claim ⊆ Evidence ⊆ Established Scope`; this is a **Python model check**, not a formal theorem or regulatory certification.
- `test_phase0.py`: tests with separate GAT, PEP, fixture, STRANGER, ledger and audit processes for every scenario.
- `ledger.jsonl`: generated by test execution when `KAIROSEED_PHASE0_LEDGER_PATH` is specified. It is intentionally **not hand-authored or committed as a static fixture**; GitHub CI uploads it as an execution artifact. Do not hand-edit the archived evidence.

## Run in a controlled local environment

Python 3.10+; standard library only. From repository root:

```sh
python -m unittest discover -s kairoseed-phase0 -p test_phase0.py -v
```

To generate a research JSONL ledger in a local working directory:

```sh
KAIROSEED_PHASE0_LEDGER_PATH=kairoseed-phase0/ledger.jsonl python -m unittest discover -s kairoseed-phase0 -p test_phase0.py -v
```

The test runner keeps per-test evidence in isolated temporary directories; when the output variable is provided it appends research case summaries to `ledger.jsonl`. Every invocation produces a **new set of test events**. The file's existence does not prove that its records were produced by a trusted, independent observer.

## Evidence and trust gaps

1. The mock protected state lives in a fixture child process reachable over Python IPC. Dedicated observation and effect channels model role separation but **do not prove OS-enforced isolation**.
2. HMAC keys and the test principal are generated by the test runner. They are not external signatures or an independently trusted Principal. A real adversary with access to test keys could forge receipts.
3. `time.time_ns()` is a service-side clock read, **not attested or monotonic across clock adjustments**. We do not claim clock-skew hardening.
4. Revocation is queried at the authorization step, **not proven to propagate instantly across concurrent operations**. No post-authorization revocation linearizability claim.
5. Hash-linked JSONL is **tamper-evident only under its threat assumptions**, not WORM or independently anchored. A test of a damaged copy does not prove privileged full-ledger rewrite resistance.
6. STRANGER reads fixture state directly over a restricted test channel, but verification shares the fixture's process and machine trust dependencies.
7. Denied action with mock delta zero is a narrow boolean result. It does not show absence of arbitrary filesystem, network, operating-system or external effects.
8. The harness contains a synthetic trap and failure cases; successful TC-10 cannot establish detection or prevention of real direct syscalls.
9. All test pass/fail claims must cite the exact GitHub Actions run, checked-out commit and raw logs. A PR description or README is only a specification.

**Decision semantics:** PASS = tests observed under these conditions, FAIL = specific test contradiction, NOT VERIFIED = untested security boundary. **No broader assurance upgrade from a green test suite.**
